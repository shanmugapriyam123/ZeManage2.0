Installation Steps

  1. Download and run ZeManageSetup.exe from the distribution provided by your administrator.
  2. Review and accept the Privacy Policy.
  3. Enter your license key (provided by your company or project administrator).
  4. Select the Revit versions you want to install for (multi-version supported).
  5. Complete the installation wizard and restart Revit.

License Activation & Device Registration

On first launch after installation, ZeManage will prompt you to register your device. This links your machine to your organization's license. Each license key supports a configurable number of devices.

Quick Start Guide

Get up and running with ZeManage in minutes. Follow this first-time setup flow:

  1. Open Revit — After installation, the ZeManage ribbon tab appears in the Revit toolbar.
  2. Sign In — Click the ZeManage tab and authenticate with your license credentials. Your device will be registered automatically.
  3. Register Your Model — Open a Revit model and register it via ZeManage > Model Registration. Each model receives a unique GUID for tracking.
  4. Configure Sync Settings — Set your preferred background sync interval, relinquish timeout, and scheduling window.
  5. Explore the Dashboard — Open the Health Monitor to view your model's health score and key metrics.
  6. Set Up Protection (Admins) — Configure pin protection, command restrictions, event rules, and rule-based protection as needed.

Tip: Import a pre-configured .ze file from your administrator to instantly apply sync and protection settings.

Protection

ZeManage provides four layers of model protection to enforce BIM standards and prevent unauthorized changes. Each layer can be configured independently at the company, project, or model level.

Pin Protection

Lock individual elements to prevent accidental modification. Protected (pinned) elements cannot be moved, deleted, or modified without explicit admin authorization. Pin protection is especially useful for critical elements like grids, levels, and reference planes.

  • Pin elements individually or by selection set
  • Visual indicators show which elements are protected
  • Unpinning requires administrator override (OTP or password)

Command Protection

Control which Revit commands can be executed on protected elements. Each command can be set to one of three protection modes:

Protected CommandsAvailable Modes
Delete, Cut, Copy, Move, Rotate, Mirror, Group, Unpin Notify Assist Protect

Notify

Logs the action for audit purposes. The user is informed but allowed to proceed with the operation.

Assist

Shows a guidance dialog explaining the policy. The user can choose to proceed or cancel the action.

Protect

Blocks the action entirely. Requires OTP or admin password to override and proceed.

Event Restriction

Restrict Revit-level events based on company policies. Event restrictions fire automatically when a user attempts a restricted action:

EventDescription
Open from non-approved locationBlock opening files from unauthorized network paths or local drives
Open central file directlyPrevent users from opening central models instead of creating local copies
Model upgrade protectionBlock upgrading models to a newer Revit version without authorization
Save over earlier versionPrevent saving a model that would overwrite an earlier file version
CAD import / explodeBlock importing or exploding CAD files to maintain model purity
Sync conflict detectionDetect and alert on synchronization conflicts with central model
Family loading / version mismatchControl family loading and flag version mismatches
Revit Link pin promptPrompt users to pin Revit links after loading

Rule-Based Protection

Define custom rules based on parameters, categories, or element types. Rules are evaluated in real time as users interact with the model.

ScopeDescriptionManaged By
Company-wideApplied across all projects and models in the organizationCompany Admin
Project-wideApplied to all models within a specific projectProject Admin
Model-specificApplied to a single model onlyProject Admin

Rules sync to the cloud via REST API and are pushed in real time to all connected clients via SignalR. Changes made offline are queued and applied when connectivity is restored.

Admin Override

When a user encounters a protected action, administrators can authorize the operation using:

  • OTP (One-Time Password) — A single-use code generated by an admin, valid for one override action.
  • Admin Password — Direct password entry for immediate override authorization.
  • Evidence Capture — Automatic before/after screenshots are captured for every override to maintain a complete audit trail.

Activity Tracker

Journal Analysis: The Crash Register automatically parses Revit journal files to identify the likely cause of crashes, helping teams diagnose and prevent recurring issues.

User Roles

ZeManage uses a role-based access control system with three tiers. Roles determine what features a user can configure and manage.

RoleAccess LevelCapabilities
Company Administrator Full Access All features across all projects. Configure company-wide protection rules, commands, events, and user management. Generate OTPs. View all audit logs.
Project Administrator Project-scoped Manage assigned projects. Configure project/model-level protection, rules, and sync settings. View project-level audit data.
Normal User Standard Work within defined protections. View session info, health dashboard, sync settings, and personal activity. Request overrides via OTP.

Session role-swapping is supported — administrators can temporarily operate as a Normal User to test the end-user experience without changing their actual role assignment.

Evidence Capture

When a protected action is overridden, ZeManage automatically captures screenshots of the affected area before and after the operation. This visual evidence is stored with the audit log entry and synced to the cloud for review by administrators.

OTP Management

One-Time Passwords (OTPs) provide a secure mechanism for administrators to grant temporary override access to protected operations without sharing admin credentials.

  • Generation — Company and Project Administrators can generate OTPs from the admin panel.
  • Single Use — Each OTP is valid for exactly one override action and expires after use.
  • Audit Trail — OTP usage is logged with the override action, including who generated it and who used it.
  • Expiration — OTPs have a configurable expiration window for security.

Troubleshooting & FAQ

Frequently Asked Questions

ZeManage tab is not visible in Revit

Ensure the plugin is installed for the correct Revit version. Check %AppData%\Autodesk\Revit\Addins\ for the ZeManage .addin manifest file. Restart Revit after installation.

Unable to connect to cloud services

Verify your internet connection and check that your organization's firewall allows outbound HTTPS traffic. ZeManage will automatically switch to offline mode and queue operations for later sync.

License activation fails

Confirm that your license key is entered correctly (no leading/trailing spaces). If the key has been used on the maximum number of devices, contact your Company Administrator to deactivate an existing device.

Sync is not running on schedule

Check the Sync Control settings to ensure the schedule window is configured correctly. Background sync requires the Revit model to be open and saved at least once. Verify the sync mode (Continuous vs When Paused) matches your expectations.

Health Monitor shows no data

Run the Analyze Model function from the Health Monitor panel. The initial analysis must be triggered manually; subsequent analyses run according to your configuration.

OTP code is not working

OTP codes are single-use and have an expiration window. Verify the code has not already been used or expired. Request a new OTP from your administrator if needed.

Crash Recovery: If Revit crashes while ZeManage is active, all unsynchronized data is preserved in the local database. On next launch, the offline queue will automatically process pending operations.

Login Flow Guide

End-to-end reference for how authentication works in the ZeManage Revit plugin: ribbon click → API call → token storage → ribbon update, including token refresh, logout, the two-token model (device vs admin), and failure paths.

High-Level Flow Diagram

[Revit Ribbon: "Sign In" button] ↓ SignInCommand.Execute() —— pulls auth services from DI ↓ SignInDialog (WPF window) —— owned by Revit main window ↓ SignInViewModel —— if already authenticated, restore from disk ↓ User types email + password → SignInAsync() ↓ AuthApiService.AdminLoginAsync(machineId, sessionId, email, password) ↓ POST {ApiBaseUrl}/api/v1/tenant/device/auth/admin-login ↓ LoginResponse { accessToken, refreshToken, roleName, profileId, ... } ↓ AuthTokenManager.SetTokensFromLogin() • access token → memory (admin slot) • refresh token → %APPDATA%\BIManage\auth.dat (DPAPI) • _isAdminSession = true ↓ Build UserIdentity → UserService.SetCurrentUser() ↓ SecureTokenStorage.SaveUserIdentity() → %APPDATA%\BIManage\identity.dat (DPAPI) ↓ ViewModel.IsAuthenticated = true → dialog swaps to "signed-in" view ↓ SignInCommand → RibbonVisibilityManager.UpdateAllButtonVisibility() ↓ ✓ Logged in. Subsequent API calls use AuthenticatedHttpClient which attaches Bearer token and auto-refreshes on 401.

Step-by-Step

1. Entry — Ribbon click

Ribbon button registered in Application.cs:3060. Triggers SignInCommand (an IExternalCommand).

2. Command pulls services from DI

SignInCommand.cs:19-89 resolves from ServiceRegistry: AuthApiService, AuthTokenManager, IUserService, SecureTokenStorage, SessionSyncService, IRevitContext, ILogger. If any are missing → TaskDialog "Authentication services not available", abort.

3. Show SignInDialog

SignInDialog.xaml.cs — borderless modal, owned by Revit main window. Constructs SignInViewModel with the services from step 2.

4. ViewModel init — restore prior session if any

SignInViewModel.cs:104-126. If IUserService.IsAuthenticated, repopulate AuthenticatedUser, Email, CompanyDisplay, RoleDisplay from SecureTokenStorage — user lands directly on "signed-in" view, no re-login needed.

5. User enters credentials, clicks Sign In

Email + password fields with placeholder + show/hide toggle.

6. Validate and call API

SignInViewModel.SignInAsync(). Validates: email non-empty, valid format, password non-empty. Gets machineId via MachineIdentifier.GetMachineId() + session ID from IRevitContext. Calls _authApi.AdminLoginAsync(machineId, sessionId, email, password).

7. HTTP POST

AuthApiService.cs:304-328. POST {ApiBaseUrl}/api/v1/tenant/device/auth/admin-login with body { machineId, sessionId, username, password }. ApiBaseUrl = https://api.zemanage.com (from App.config).

8. Token storage on success

AuthTokenManager.SetTokensFromLogin():

  • Access token → memory only (_adminAccessToken, expires per tokenExpiry or +1h)
  • Refresh token → DPAPI-encrypted file %APPDATA%\BIManage\auth.dat
  • Sets _isAdminSession = true so future refreshes hit /admin-refresh (not /refresh)
  • Two parallel token slots exist: admin (has profileId, for writes) vs device (heartbeats); admin wins when both present

9. Identity persisted

Parses roleName → IsCompanyAdmin / IsProjectAdmin flags. Builds UserIdentity (userId, email, companyId, profileId, role flags, admin token). _userService.SetCurrentUser(identity) — in-memory. _secureStorage.SaveUserIdentity(...) — DPAPI-encrypted to %APPDATA%\BIManage\identity.dat.

10. UI swaps to signed-in view

Hides form panel, shows signed-in panel with role badge:

  • C Company Admin — "Full access across all projects"
  • P Project Admin — "Manage assigned projects"
  • U User — "Standard access with protections"

11. Ribbon refresh

On dialog.Success == true, calls RibbonVisibilityManager.UpdateAllButtonVisibility() to reveal admin-only buttons per role flags.

Bootstrap (happens once at Revit startup, before any login)

RevitBootstrapper.cs:741-781:

  • Creates and registers as singletons: SecureTokenStorage, AuthApiService, AuthTokenManager, AuthenticatedHttpClient
  • If identity.dat exists and contains a ProfileId, calls tokenManager.RestoreAdminSessionFlag(true) — ensures refresh routes to /admin-refresh even before first user action

How subsequent API calls stay authenticated

AuthenticatedHttpClient.SendWithAuthAsync():

  1. Pull current token via tokenManager.GetAccessTokenAsync()
  2. Attach Authorization: Bearer <token>
  3. If response is 401:
    • Force-expire in-memory token
    • Call GetAccessTokenAsync() again → triggers refresh against /admin-refresh
    • Retry the request once
  4. If retry also 401 → fire AuthExhausted event → user must re-login

Refresh internals: AuthTokenManager.RefreshAccessTokenAsync() — on 400/401/403 throws TokenRejectedException and wipes the stored refresh token (it's revoked); on network errors keeps the refresh token for retry.

Logout

SignInViewModel.SignOut():

  1. Fire-and-forget POST /api/v1/tenant/device/auth/admin-logout with sessionId + admin token (server-side revoke)
  2. tokenManager.ClearTokens() — wipes both memory slots + deletes auth.dat
  3. secureStorage.ClearUserIdentity() — deletes identity.dat
  4. userService.Logout() + UserDisplayNameCache.Clear()
  5. ViewModel flips back to form view

Auto-logout triggers

AuthExhausted 401 with no stored refresh token (throttled to 1/2min) Wipe all tokens, prompt re-login

Device Token vs User (Admin) Token — When Each Is Obtained

The app maintains two parallel token slots in AuthTokenManager.cs:24-33:

SlotFieldSource endpointHas profileId?Used for
Device _deviceAccessToken / _deviceExpiresAt POST /validate-device (machineId only, no password) No Heartbeats, session sync, read-only metrics
Admin _adminAccessToken / _adminExpiresAt POST /admin-login (email + password) Yes Protection writes, command/event/rule changes

_isAdminSession flag routes refresh: true → /admin-refresh, false → /device/auth/refresh.

Timeline — when each token is obtained

T0 Revit launches | T1 RevitBootstrapper.Initialize() runs (logging, core, identity, persistence) | -- no auth yet | T2 RegisterApiServices() phase | -- SecureTokenStorage created -> loads persisted refresh token + identity.dat | -- AuthApiService, AuthTokenManager, AuthenticatedHttpClient registered | -- If identity.dat had ProfileId -> RestoreAdminSessionFlag(true) | (routes future refresh to /admin-refresh) | T3 AutoAuthenticateDeviceAsync() fires (background, 5s timeout, non-blocking) | [RevitBootstrapper.cs:1486-1555] | | | +-- Step A: Try stored refresh token | | GetAccessTokenAsync() -> if admin flag set: /admin-refresh, | | else: /device/auth/refresh -> populates the matching slot. | | | +-- Step B: If no stored token, call ValidateDeviceAsync(machineId) | | POST /validate-device body: { "machineId": "..." } | | SetTokensFromDevice() [AuthTokenManager.cs:186-211] | | - _deviceAccessToken / _deviceExpiresAt populated | | - device refresh token persisted ONLY if no admin session | | | +-- Step C: If validation fails -> red device-status icon, no dialog | T4 SignalR connects using GetAccessTokenAsync() as bearer source | -- prefers admin if _isAdminSession, else device | T5 SessionSyncService heartbeat starts (uses device token) | =================================================================== T6 User clicks Sign In on ribbon <-- ADMIN TOKEN ONLY OBTAINED HERE | SignInViewModel.SignInAsync() | AuthApiService.AdminLoginAsync(machineId, sessionId, email, password) | POST /admin-login | -> | SetTokensFromLogin() [AuthTokenManager.cs:162-176] | - _adminAccessToken / _adminExpiresAt populated | - _isAdminSession = true | - refresh token (admin) persisted to auth.dat | - DEVICE slot is NOT touched -- both tokens now coexist | T7 Subsequent API requests | -- AuthenticatedHttpClient picks the right slot per requireAdminToken flag | - admin-scoped writes -> GetAdminAccessTokenAsync() | - device-scoped heartbeats -> GetDeviceAccessTokenAsync() | -- On 401, force-expire that slot, refresh from matching endpoint, retry once ===================================================================

Key timing facts

  1. Device token is obtained automatically at startup — no user action required. Just needs machineId (no password).
  2. Admin token is obtained ONLY when the user manually clicks Sign In. It is never fetched on startup, even if identity.dat exists — the refresh token persisted there is used to renew the admin access token, but the access token itself lives only in memory and is re-minted on demand.
  3. Both tokens can be held simultaneously. Signing in does NOT replace the device token; it adds the admin token alongside it.
  4. Logout clears both slots and both .dat files. Demoting an admin clears only the admin slot via ClearAdminTokens().

Why two tokens?

  • Server enforces that admin-scoped writes (protections, rules, audit logs) require a token with the profileId claim — only /admin-login issues that.
  • Device endpoints (heartbeat, session sync, telemetry) only need machine identity — /validate-device issues a profileId-less token for that.
  • Keeping them separate means a device heartbeat won't consume/refresh the admin token, and admin sign-out doesn't kill device telemetry.

Verification — testing the flow live

  1. Start Revit, click the Sign In ribbon button → confirm SignInDialog opens
  2. Enter valid credentials → confirm dialog swaps to "signed-in" view with role badge
  3. Check %APPDATA%\BIManage\ for auth.dat and identity.dat (should both exist after login)
  4. Close and reopen Revit → click Sign In again → should show "signed-in" view directly (restored from identity.dat)
  5. Click Sign Out → both .dat files should be deleted
  6. Enter wrong password → confirm "Invalid email or password." message

Switching environments (e.g., staging → production): The local .dat files are issued by a specific server. If you change ApiBaseUrl, the old tokens will be rejected. Delete %APPDATA%\BIManage\auth.dat and identity.dat, then re-register the device and sign in fresh against the new environment.
